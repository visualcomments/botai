# Локальный журнал и предложения самоулучшения

Механизм фиксирует короткие проверяемые наблюдения о **самой обвязке botai** и помогает подготовить локальное изменение. Это не обучение модели и не автоматическая правка политики. Он не читает учебные досье, попытки, курсы или полные разговоры и не отправляет данные в сеть.

Подробная спецификация и ограничения реализации: [self-improvement-design.md](self-improvement-design.md).

## Быстрый старт

Все команды выполняются из корня checkout/workspace. Состояние хранится в `.botai/self_improvement/` и исключено из Git.

```bash
python3 scripts/cli.py self-improve status
python3 scripts/cli.py self-improve recover
python3 scripts/cli.py self-improve triage --limit 20
python3 scripts/cli.py self-improve migrate --learner-id self-improvement
python3 scripts/cli.py self-improve capture \
  --kind error --area cli \
  --summary "Команда не сообщала понятную причину ошибки" \
  --source-type file --source-ref tests/test_self_improvement.py
python3 scripts/cli.py self-improve search --query cli
```

`capture` сохраняет только короткую сводку и ссылку на источник. Не вставляйте токены, пароли, полный вывод команд/модели, содержимое задания или личные данные. Встроенная очистка секретов — лишь дополнительный фильтр, а не гарантия обезличивания.

## Проверка вывода

Новая запись получает `claim: unknown — needs triage` и `validation: pending`. Перед использованием как правила укажите точное подтверждение:

```bash
python3 scripts/cli.py self-improve review \
  --entry LRN-YYYYMMDD-ABC --expected-version 1 \
  --claim "Узкое утверждение с указанной областью" \
  --evidence-type file --evidence-ref Makefile \
  --result "Проверено человеком по текущему исходнику" \
  --validation verified --scope "текущая версия рабочего пространства"
```

`verified` допускается только со ссылкой на существующий локальный файл (ядро проверит, что это файл внутри workspace) либо на решение maintainer/исходный код команды, фактическую проверку которых должен выполнить и описать человек. Ссылка `test` не считается выполненным тестом и не принимается для `verified`. Это фиксация доверенного человеческого review, не автоматическое доказательство правильности. Недоступный/противоречивый источник остаётся `unresolved`/`contradicted`; число наблюдений не растёт при review или перечитывании.

Для устаревшей или опровергнутой записи используйте явную архивацию с текущей версией:

```bash
python3 scripts/cli.py self-improve retire \
  --entry ERR-YYYYMMDD-ABC --expected-version 2 \
  --reason "Новое подтверждённое поведение заменило наблюдение"
```

`retire` не удаляет запись и evidence, требует актуальную версию, сохраняет причину и исключает запись из активного `search`.

## Предложение изменения

В первой версии разрешены только существующие Markdown-файлы под `docs/self-improvement-guidance/`. Эти документы не загружаются автоматически в системные инструкции: их использование/публикация — отдельный ручной шаг. `AGENTS.md`, политика помощи, consent-gate, безопасность, схемы, курсы, прогресс, настройки агента и код закрыты для изменения. `verify` проверяет структуру, UTF-8 и контрольные хеши; он **не** выполняет тесты и не проверяет семантическую безопасность или педагогическую правильность. Шлюз фраз не является доказательством безопасности. Человек обязан прочитать весь diff и отклонить изменения, затрагивающие политику или ослабляющие ограничения. Это workflow подтверждения, а не техническая изоляция от процесса с правами владельца workspace.

```bash
python3 scripts/cli.py self-improve propose \
  --entry LRN-YYYYMMDD-ABC \
  --target docs/self-improvement-guidance/cli.md \
  --old-text "старый точный фрагмент" \
  --new-text "предлагаемый фрагмент" \
  --rationale "Почему это изменение следует из проверенной записи"
python3 scripts/cli.py self-improve preview --proposal <ID>
python3 scripts/cli.py self-improve verify --proposal <ID>
```

До создания proposal целевой файл должен существовать. Предложение отклоняется, если точный старый фрагмент не встречается ровно один раз.

### Подтверждение и применение

Только интерактивный терминал; не вызывайте `approve`/`apply` из фонового агента, MCP или сценария.

```bash
python3 scripts/cli.py self-improve approve --proposal <ID>
```

CLI показывает diff и предупреждает, что структурная проверка не оценивает смысл. До подтверждения человек обязан прочитать diff и самостоятельно решить, что он не меняет политику, ограничения помощи или согласие. Затем вводится `approve <ID>`, после чего выдаются `approval_id` и одноразовый `challenge` на пять минут. Это решение человека; данный прототип не может надёжно классифицировать произвольный текст как неослабляющий политику. Затем:

```bash
python3 scripts/cli.py self-improve apply \
  --proposal <ID> --approval <APPROVAL_ID>
```

CLI снова показывает diff, просит подтвердить `apply <ID>` и ввести challenge. Применение отказывает, если исходный файл или fingerprint proposal изменился, код не совпал, challenge использован/истёк или proposal не прошёл структурную проверку. Человек несёт ответственность за смысловой review; синтаксический/структурный отчёт не является разрешением ослабить политику. После успешного применения `application_id` нужен для отката:

```bash
python3 scripts/cli.py self-improve revert --application <APPLICATION_ID>
```

Откат возможен только если файл всё ещё совпадает с применённым вариантом; более поздние ручные изменения не перезаписываются.

Локальный интерактивный challenge снижает риск случайного запуска из инструмента, но **не защищает от вредоносного процесса с правами того же пользователя**, который может изменять локальные файлы состояния. Это workflow с подтверждением, не граница ОС и не гарантия, что сама модель не сформулирует ошибку текстом.

## Использование через Makefile

```bash
make self-improve ACTION=status
make self-improve ACTION=capture ARGS='--kind error --area cli --summary "сообщение об ошибке неясно"'
make self-improve ACTION=search ARGS='--query cli'
```

Для остальных параметров используйте `python3 scripts/cli.py self-improve help` или `python3 scripts/cli.py self-improve <подкоманда> --help`. Параметры принадлежат подкомандам и не конфликтуют с флагами основного workspace CLI.

## Что пока не поддерживается

- автоматический анализ/сохранение транскрипта и hook на каждую сессию;
- автоматическое добавление записей в системные инструкции или активные навыки;
- применение Python-кода, произвольных команд, изменения учебной политики или контракта курса;
- авто-коммит, push, GitHub API, PR, токены и внешняя телеметрия;
- семантическая проверка текста guidance или доказательство улучшения результатов обучения;
- защита файловой системы от вредоносного процесса с теми же правами пользователя (workspace — доверенная граница).

Предпочтения конкретного ученика должны оставаться в соответствующем consent/progress механизме, а не попадать в общую память workspace.
